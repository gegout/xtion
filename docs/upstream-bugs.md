# Upstream behavior and applicability

High-confidence source observations refer to [OpenNI2 PS1080 Sensor](https://github.com/OpenNI/OpenNI2/tree/115cf06c6efea32304182d293eca16ca883c9150/Source/Drivers/PS1080/Sensor).

* XnSensorDepthStream.cpp starts the endpoint reader before writing stream settings. CloseStreamImpl writes stream 1 OFF before cancelling reads. XnCmosInfo::SetCmosConfig fetches and caches algorithm coefficients on firmware 5.1 and newer.
* XnHostProtocol.cpp checks command IDs, polls for replies and retries SET_PARAM up to five times in selected cases. The initial stream-1 receive delay defaults to 300 ms and drops to 1 ms on newer firmware outside the low-bandwidth path. SOFT_FIRST uses SET_MODE and the mode-switch code ignores its return status. These paths do not promise that an ordinary parameter write always receives an ACK.
* XnDeviceSensorIO.cpp uses alternate settings from firmware tables, bulk command endpoint detection and EP0 on modern devices. XnDataProcessor.cpp tolerates a zero packet ID. Within-frame resets can conceal loss without checking the final payload size.
* The [structureio fork](https://github.com/structureio/OpenNI2/tree/3b787cc8b06e4129d1c5d7daf99e04413ac42266) has an identical XnHostProtocol.cpp in the inspected revisions. Its [issue 125](https://github.com/structureio/OpenNI2/issues/125) concerns RGB exposure, a different symptom.
* [PrimeSense Sensor](https://github.com/PrimeSense/Sensor/tree/60170bfe8de166b2947ea2d604506f0bdfa0565c) corroborates stream-specific polling delays. [SensorKinect](https://github.com/avin2/SensorKinect/tree/15f1975d5e50d84ca06ff784f83f8b7836749a7b) is a derivative with device-specific behavior. [Debian's Linux USB transport](https://sources.debian.org/src/openni2/2.2.0.33%2Bdfsg-7%2Bdeb9u1/ThirdParty/PSCommon/XnLib/Source/Linux/XnLinuxUSB.cpp) uses multiple submitted transfers and libusb events. No reviewed patch establishes a fix for the exact 5.8.22 shutdown symptom.

[Upstream release history](https://github.com/OpenNI/OpenNI2/blob/115cf06c6efea32304182d293eca16ca883c9150/CHANGES.txt) includes Linux identification and lifetime fixes. Source comparison did not identify an exact-device bug report proving why early stream-enable polling coincided with the original control failure. Confidence in a specific firmware defect remains low.

The vendored libusb synchronous implementation submits a transfer and services completion events in sync_transfer_wait_for_completion. A separate application event loop is unnecessary for these synchronous rusb calls. rusb 0.9.4 returns Ok(n) for timeout/interruption with positive transferred length. Thus a reported timeout from read_bulk carries zero bytes and cannot by itself prove a packet gap. [libusb synchronous transport](https://github.com/libusb/libusb/blob/master/libusb/sync.c), [rusb DeviceHandle](https://docs.rs/rusb/0.9.4/src/rusb/device_handle.rs.html)

USB packets are protected by the USB transport. The reconstructed PS1080 data header supplies length, sequence, type and timestamp. Xtion cannot detect an arbitrary pixel substitution that preserves all of these and the encoded frame length. Frame completeness establishes structural validity. Optical accuracy still requires a physical reference.
